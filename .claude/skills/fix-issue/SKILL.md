## 工作流程

**第一步：进入 Plan 模式**

你必须先使用 EnterPlanMode 进入计划模式。在计划模式中完成以下分析后，再开始编码。

**第二步：问题验证（Plan 模式内）**

在动手修复之前，先确认问题是否真实存在：

1. **全链路追踪** — 根据问题类型追踪完整调用链：
   - **前端问题**：组件 → Zustand store → `invoke()` IPC 调用 → Tauri command → service 层
   - **后端问题**：Tauri command → service 层 → 外部依赖（文件系统/keychain/子进程）
   - **跨层问题**：前端 invoke 参数 → Rust 命令签名 → 序列化/反序列化边界
2. **区分问题层级** — 明确问题出在哪一层：
   - **组件层**（React 渲染/交互逻辑）
   - **状态层**（Zustand store 状态管理/数据流）
   - **IPC 层**（invoke 调用/参数传递/错误处理）
   - **命令层**（Tauri command 参数校验/响应格式）
   - **服务层**（Rust 业务逻辑/外部集成）
   - **上游依赖层**（`smcp-computer` crate 等第三方/团队内部依赖）
3. **判定问题归属** — 特别注意区分：根因在本项目（tfrobot-client）还是在上游依赖（尤其是 `rust-sdk` 仓库的 `smcp-computer` crate）。参见下方「上游依赖问题处理原则」。
4. **排除误报** — 如果问题实际不存在或属于使用姿势问题，直接说明原因并结束

**第三步：根因分析与方案设计（Plan 模式内）**

确认问题存在后，进行架构级分析：

1. **根因分析** — 不只看表面症状，要找到根本原因。问自己：
   - 同类问题在其他模块是否也存在？
   - 这是设计缺陷还是实现疏忽？
   - 修补表面症状是否会在其他地方引发新问题？
2. **影响面评估** — 修改会影响哪些组件、store、命令、测试？
3. **方案设计** — 必须符合以下架构原则：

### 架构原则（强制遵守）

**Rust 后端：**
- **命令层职责清晰**：`commands/` 只做参数接收、调用 service、格式化返回值；业务逻辑在 `services/` 中实现
- **错误处理一致性**：Tauri command 统一返回 `Result<T, String>`，service 层使用具体错误类型，command 层负责转换为用户友好的错误消息
- **异步安全**：所有涉及 IO 的操作使用 async，注意 Tauri state 的线程安全（`Mutex`/`RwLock`）
- **资源生命周期**：通过 Tauri 的 `manage()` 管理共享状态，避免全局可变静态变量

**TypeScript 前端：**
- **组件职责单一**：组件只负责 UI 渲染和用户交互，业务逻辑放在 Zustand store 中
- **Store 设计规范**：每个 store 负责一个独立的领域（mcp/connection/logs 等），store 之间不直接互相引用
- **IPC 调用集中**：所有 `invoke()` 调用应在 store 的 action 中，组件不直接调用 invoke
- **错误处理统一**：invoke 调用必须有 try/catch，错误信息通过 store 状态暴露给组件
- **国际化完整**：用户可见的文本必须使用 `t()` 函数，不允许硬编码字符串

**跨层约定：**
- **类型安全**：Rust 的 serde 序列化结构必须与 TypeScript 类型定义保持一致
- **命名一致性**：Rust command 使用 snake_case，TypeScript invoke 使用对应的 snake_case 字符串
- **防御性编程**：前端不假设后端一定返回成功；后端不假设前端传参一定合法

### 上游依赖问题处理原则（强制遵守）

`rust-sdk` 仓库（路径 `/Users/jqq/RustroverProjects/rust-sdk`）中的 `smcp-computer` crate 由团队内其他同事维护。当问题根因定位到此库时，必须遵守以下原则：

1. **绝不修改上游代码** — 即使我们能看到 `rust-sdk` 的源码，也不要直接修改。这是其他同事的职责范围。
2. **输出 Bug Report** — 将问题整理为结构化的 Bug Report，包含：
   - **问题标题**：简明扼要描述问题
   - **复现路径**：从 tfrobot-client 的哪个功能触发，调用了 `smcp-computer` 的哪个 API
   - **期望行为 vs 实际行为**
   - **相关代码引用**：指出 `smcp-computer` 中的具体文件和行号
   - **建议修复方向**（可选）：如果有明确思路可以附上
3. **不跳过、不标记 skip 测试** — 如果我们的测试因上游问题而失败，保留测试原样。测试失败本身就是对上游修复的验收标准。将我们的利益与上游绑定在一起，而不是各自为战。
4. **解决路径** — 明确告知用户：此问题需转发给 rust-sdk 开发者修复 → 他们发布新版本 → 我们升级 `smcp-computer` 依赖版本 → 测试通过。
5. **临时适配层（仅在必要时）** — 如果上游问题阻塞了我们的核心功能且短期内无法修复，可以在 tfrobot-client 的 service 层添加临时适配代码（必须标注 `// WORKAROUND: waiting for smcp-computer fix, see Bug Report #xxx`），但绝不修改上游源码。

### 一致性检查

修复时必须检查：
- 同模块其他功能是否有相同问题（批量修复，不留隐患）
- 修改是否与现有代码风格一致（命名、错误处理、日志格式）
- 是否需要同步更新国际化翻译文件（`src/locales/`）
- Rust 和 TypeScript 的类型定义是否保持同步

**第四步：制定修复计划（Plan 模式内）**

输出结构化计划，包含：
- **问题确认结论**（存在/不存在/部分存在）
- **根因归属**（tfrobot-client 本项目 / smcp-computer 上游依赖 / 两者兼有）
- **根因说明**（一句话说清根本原因）
- 若根因在上游：输出 **Bug Report**（按「上游依赖问题处理原则」中的格式），并说明升级路径
- 若根因在本项目：输出 **修改文件清单**（每个文件的具体变更内容）
- **测试计划**（新增/修改哪些测试用例来覆盖此问题，确保不再复发。注意：因上游问题导致的测试失败不得跳过或标记 skip）
- **验证步骤**（如何确认修复生效）

然后使用 ExitPlanMode 提交计划等待审批。

**第五步：实现与测试（审批后）**

1. 按计划逐文件修改
2. 每个修改点必须有对应的测试覆盖：
   - Rust 端：在对应模块添加 `#[cfg(test)]` 单元测试
   - 前端端：在 `src/test/` 下添加或更新对应的测试文件
3. 运行验证：
   - 前端类型检查：`pnpm build`
   - 前端测试：`pnpm test`（如有配置）
   - Rust 编译检查：`cd src-tauri && cargo check`
   - Rust 测试：`cd src-tauri && cargo test`
4. 如果修改涉及国际化，确认中英文翻译文件均已更新
