# 场景设计指南：Tauri 协同 UAT

> 本指南是 tfrobot-client UAT 的唯一设计参考。所有场景都走协同模式，不适用于
> Playwright 自动化假设。

## 为什么要有独立指南

Web 项目的 UAT 设计指南（fsm-lifecycle / payment-async / rbac-permission）都隐含同一个假设：
**Claude 能驱动浏览器自己跑场景**。因此它们关心状态机图、断言时序、截图时机。

Tauri 项目不是：Claude 不能自动点按钮，不能自动填表，也不能自动截图。一切用户操作都要
靠人。于是设计重点变了：

| 维度      | Web Playwright | Tauri 协同        |
|----------|---------------|-------------------|
| 谁操作 UI  | Claude         | 用户               |
| 谁校验     | Claude（屏幕快照 + DOM）| Claude（日志） + 用户（肉眼） |
| 反馈通道   | 同步（Claude 自检）| 异步（用户贴回）   |
| 节奏控制   | Claude 按节奏推进 | 一步一 ping pong   |
| 失败定位   | Claude 看 console / network | Claude 读用户贴回的日志 |

## 核心设计原则

### 1. 每条用例必须四段式

这是本项目最重要的约束。任何用例没有下面四段的都不合格：

```
**做什么**: 一句动宾结构
**复制用**: 用 `inline code` 包的数据块（用户一键复制）
**应该看到**: UI + Console 两层
**失败时贴什么回来**: 具体物料清单
```

**为什么**：

- "做什么"是一个动作 → 用户不会搞错
- "复制用"是 inline code → 避免用户手打错字
- "应该看到"分 UI / Console 两层 → Claude 有客观标准可验（Console），不完全依赖用户主观判断
- "失败时贴什么回来" → 避免用户反馈 "挂了" 这种 0 信息量消息

### 2. 优先用 Console 日志做断言锚

客户端前端用 `@tauri-apps/plugin-log` 的 `info()` / `warn()` 打日志，格式固定以 `manager:`
开头（或其他业务模块前缀）。这是 Claude **可以 grep 可以 regex** 的硬标准。

**推荐**：在用例"应该看到"里写出期望的日志行模式：

```
Console: `manager: login ok, accountId=<number>`
Console: `manager: fetched <N> digital employees`
```

**不推荐**：只写"登录成功"——Claude 没法客观校验"成功"。

### 3. 主动验证脱敏 / 安全敏感点

客户端有一条用户明确提出的安全要求：**日志里不得出现明文 access_token / JWT**。这类点
不能靠用户眼力看，必须靠 Claude 在用户贴回日志后 regex 验一次：

```
Claude 在用户贴日志后主动跑：
- 不能含 64 字符 hex: ! /[a-f0-9]{64}/
- 必须有 `"access_token":"***"` 字面量
- 不能出现顶层 `"accessToken":` 键
```

把这类校验独立列在场景文档的"关键断言点"小节，不要淹没在普通用例里。

### 4. BLOCKED 不是失败，是分类

不是所有场景都能在本地立即跑。典型 BLOCKED 来源：

- 需要 Manager 侧提供 Mock 能力（402 / 403 / 401 触发）
- 需要 TFRobotServer 侧特殊状态（实例被删 / 配额耗尽）
- 需要生产环境才能复现（跨 VPN 等）

BLOCKED 用例不参与 PASS/FAIL 统计，但必须**标注解锁条件**，UAT 报告里单独列为 `⏸️ Z`
受阻。解锁条件满足后，通过 `/uat-scenario update` 转为 active。

### 5. 每条用例要映射到一个归属

用例失败时，`Bug 分流`要能快速定位归属。在场景文档末尾提供"失败时的 Bug 分流映射"表：

| 症状                    | 归属                        |
|------------------------|----------------------------|
| 日志出现 xxx 特征       | tfrobot-client 前端          |
| 日志出现 yyy 特征       | tfrobot-client Rust DTO     |
| curl 直接打也出错       | TFRSManager                |
| Manager 正常但 SMCP 断  | TFRobotServer              |

**原则**：归属是用例的属性之一，写场景时就要想清楚。不清楚就拆成更细的用例。

### 6. Seed 数据永远引用不硬编码

用例步骤里的手机号、密码、id 等永远引用 `seed-data.md` 里的条目：

```
✅ 好:  "用 client_uat 账号登录（手机号 13800138008 / Test@123456，见 seed-data.md §登录凭据）"
❌ 差:  "登录 UAT 账号"
❌ 差:  "用 xxx@turingfocus.cn 登录"（硬编码邮箱）
```

理由：seed 数据随后端 `cmd/seed/main.go` 变，集中引用一处便于批量更新。

### 7. 状态复用减少操作成本

用户每做一步都要真实手动操作（点按钮、切换 tab、看 DevTools），成本很高。设计用例时：

- 前后相邻用例尽量复用同一前置态（比如"登录后的员工列表页"连续跑 3-4 条用例都不需要重登）
- 破坏性用例（登出、删除）放在小节末尾
- 如果 P1/P2 用例需要跑 P0 状态作为前置，在用例的"前置"里直接引用"ML-04 完成"
  而不是让用户从头再来一遍

### 8. 批量场景要可中断/可续跑

全量模式下，一个场景跑到一半用户累了需要中断。所以：

- 每条用例独立可验证（不依赖上一条的结果，除非明确标"前置"）
- 用例间 Claude 主动保存进度（TaskList 标 completed）
- 续跑时用户说"从 ML-08 继续"就能跳过前面几条

## 反模式

| 反模式                                   | 问题                        | 正确做法                      |
|-----------------------------------------|----------------------------|-----------------------------|
| "让用户随便试试登录流程"                  | 没有可验证标准              | 四段式 + Console 模式        |
| "预期：页面正常"                          | 什么叫正常                  | 列具体文本/颜色/Tag           |
| 硬编码密码/手机号                        | seed 一变就错一堆            | 引用 seed-data.md             |
| 每条用例都让用户重登录                    | 操作成本爆炸                | 复用前置态                    |
| 403 / 402 用例不标 BLOCKED 直接让用户跑   | 跑不通但不写清楚原因         | 标 ⏸️ BLOCKED 写明解锁条件    |
| 遇到失败直接让用户自己 debug              | Claude 擅长日志分析应该挑起来 | 走 Bug 分流流程，Claude 主导定位 |
| 把 Claude 能跑的命令（curl / lsof）塞给用户 | 把 Claude 能力让给了人       | Claude 自己用 Bash 跑，汇总结果 |
